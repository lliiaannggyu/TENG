# TENG 文件管理器 · 圆屏手表文件管理器设计方案

> 目标不是把手机文件管理器缩小，而是在 **216dp 圆屏 / 2GB 级内存 / 300mAh 电池 / 单手拇指** 这四重约束下，
> 让"找到并处理一个文件"这件事在 3 次交互内完成。

---

## 0. 一页速览

| 维度 | 决策 | 为什么 |
|---|---|---|
| 布局 | 全屏铺满 + 内容圆半径 = D/2 × 0.88；骨架用官方 M3E `AppScaffold` / `ScreenScaffold` | 内接正方形方案（`boxedEdges="all"`）会浪费约 30% 横向宽度，文件名被截断成 `IMG_20…` |
| 主结构 | 单 Activity + 自持页面栈（`List<Screen>`） | 每次切页重建 Activity 会丢掉目录缓存与滚动位置，体感是"返回就重读盘" |
| 存储 | 沙盒 `java.io.File` + SAF `DocumentsContract` 双通道 | `DocumentFile.listFiles()` 对 N 个子项发 N+1 次跨进程查询，200 项目录直接卡死 |
| 权限 | 不申请任何存储权限（含 `MANAGE_EXTERNAL_STORAGE`） | 沙盒 + SAF 已覆盖 100% 功能；全盘权限是 Play 审核红线，且没有性能收益 |
| 删除 | 一律进回收站，30 天自动清理 | 圆屏误触率远高于手机，不可逆删除的代价不对称 |
| 传输 | 自定义 TCP 帧协议 + NSD 发现 + 内容 id 断点续传 | 手表上跑 HTTP 服务器是杀鸡用牛刀；协议只需 10 条消息 |
| 依赖 | **UI 一律优先官方 M3E（`androidx.wear.compose.material3`，即 Material 3 Expressive for Wear）**；Coil / Media3 / PdfRenderer / zip4j / commons-compress 只管非 UI 能力 | 自绘只剩 M3E 没有原语的三样：文件类型徽标容器、右滑区间多选手势、选择条底部压暗层 |

## 1. 圆屏几何规范

### 1.1 安全圆

```
物理屏直径 D（Configuration.screenWidthDp）
内容圆半径 R = D / 2 × 0.88
```

| 设备直径 | R（内容圆） | 边缘留白 | 圆顶部可用宽度（≈） |
|---|---|---|---|
| 192dp（小号） | 84.5dp | 11.5dp | 顶部第 1 行 ≈ 118dp |
| 216dp（基准） | 95.0dp | 13.0dp | ≈ 133dp |
| 240dp | 105.6dp | 14.4dp | ≈ 148dp |
| 280dp | 123.2dp | 16.8dp | ≈ 172dp |

垂直偏移 `dy` 处的可用半弦长：`halfChord(dy) = √(R² − dy²)`
（`RoundMetrics.halfChordAt()` 提供同一公式，用于手算任何固定元素的最大宽度。）

### 1.2 三条硬规则

1. **任何元素外沿到圆心 ≤ R**。`CircularStage` 在 debug 构建下会对越界元素打 `Log.w`，让问题在开发期暴露而不是在用户表盘上。
2. **可点区域 ≥ 40dp 且圆心距 ≤ R − 20dp**。列表行高 44dp、圆按钮 34~40dp、底部操作条整体落在 `0.72R` 处（弦宽 ≈ 132dp，容纳 3 个 34dp 按钮）。
3. **不放矩形通栏**。顶部时钟用 M3E `TimeText`（官方沿弧排版时钟组件），进度用 `LinearProgressIndicator` / `CircularProgressIndicator`，四角天然为空。

### 1.3 为什么不用 `boxedEdges="all"`

`BoxInsetLayout(boxedEdges="all")` 会把内容压进内接正方形（216dp → 152.8dp）。
对"图标 + 文件名 + 元信息"的三段式列表，这等于把每行宽度从 ~133dp 砍到 ~108dp，
`IMG_20261024_143012.jpg` 只能显示成 `IMG_2026…`，用户无法区分同批次照片。
因此根布局改为 `boxedEdges="none"`，安全区由 Compose 侧统一负责（列表靠缩放、固定元素靠极坐标）。

## 2. 交互映射

### 2.1 手势契约

| 意图 | 触屏 | 表冠 / 侧键 | 无表冠设备替代 | 反馈 |
|---|---|---|---|---|
| 滚动列表 | 上下滑 | 旋转表冠 | 右侧**边缘滚动轨**点按/拖动跳转 | 缩放 + 边缘渐隐 |
| 进入文件夹 / 打开文件 | 点按行 | — | — | 200ms Crossfade |
| 进入多选 | 长按行 | — | 行尾常驻"⋯"（设置项可开） | 触感 `LongPress` |
| 切换单项选中 | 选择态下点按 | — | — | 勾选圆点 |
| **区间多选** | **从某行向右滑，越过一行即多选一行** | — | 同上 | 每跨一行触感一次 |
| 放下选择 | 松手即提交（再次点按取消该行） | — | — | 顶部"已选 N" |
| 打开快捷菜单 | 底部边缘**上滑**（30dp 热区） | — | 点按底部小横条 | 整页推入 |
| 返回上一级 | 右滑 / 返回键 | 侧键 | 同左 | 出栈 |
| 退出选择态 | 返回 | 返回 | — | 清空选区 |

### 2.2 选择状态机

```
        长按 / 右滑起点
IDLE ───────────────────▶ SELECTING(anchor=i, keys={i})
  ▲                              │ 点按其它行 → keys ±= k
  │  返回 / 清除                 │ 右滑跨行  → keys ∪= [i..i+n]
  └──────────────────────────────┘
```

`anchor` 是区间选择的基准，只有"进入选择态的第一行"能当 anchor；
这样"右滑跨过 3 行"不会因为中途点按而把区间算歪。

### 2.3 为什么"上滑打开菜单"用热区而不是全局手势

全局上滑会与列表滚动抢事件（`ScalingLazyColumn` 需要消费竖直拖动）。
在圆底 30dp 的边缘热区做手势检测，既不影响列表，又符合"拇指从表底往上勾"的生理习惯。
热区同时渲染一根 3dp 小横条作为可发现性提示。

## 3. 信息架构

```
Home（存储环 + 7 个入口）
├─ Browse(location)  ← 逐级 push，栈深度 = 目录深度
│   ├─ QuickMenu       上滑菜单（粘贴/新建/排序/筛选/路径/位置/刷新/设置）
│   ├─ PathInput       手动输入路径
│   ├─ Viewer          图片 / 文本 / 音频 / 视频 / PDF
│   ├─ ArchiveBrowse   压缩包内容 + 解压
│   └─ ApkDetails      安装包信息 + 安装
├─ Collection(最近 | 收藏)
├─ Trash
├─ Search
├─ Devices → TransferProgress
└─ Settings
```

页面栈只保存 `Screen`（含 `Location` / `FileEntry`），模态层（确认、进度、消息、撤销、重命名）
**不进栈**，所以"返回"永远不会退到一个已经完成的进度条上。

## 4. 架构分层

```
presentation/            状态与 UI（Compose）
  FileManagerViewModel   唯一状态持有者：导航栈 / 浏览态 / 选区 / 剪贴板 / 进度 / 确认
  ui/round               RoundGeometry（极坐标舞台）、RoundComponents（弧/曲线文字/徽标/滚动轨）
  ui/home|browse|sheet|viewer|trash|search|lan|settings|common

data/
  FileRepository         目录缓存(LRU 24) + 排序过滤 + 递归搜索

core/
  model                  纯数据（FileEntry / SortSpec / SelectionState / ClipboardState / OpResult…）
  fs     StorageGateway  沙盒与 SAF 双通道读写
         FileOperator    复制/移动/重命名/新建/撤销（进度 + 取消 + 冲突策略）
         TrashRepository 回收站（payload + meta.json，30 天清理）
  archive ArchiveEngine  ZIP(zip4j) / 7z(commons-compress)，流式 + 进度 + 取消 + 安全防护
  apk     ApkTool        签名/分包/降级校验 + 系统安装器
  lan     LanProtocol    帧格式与消息
          LanDiscovery   NSD 广播/发现
          LanTransfer    服务端 + 客户端 + 断点续传
          TransferService 前台服务保活
  prefs   UserPreferences DataStore（排序偏好/收藏/最近/设备名）
  util    Formatters     体积/时间/文件名/摘要
```

依赖方向严格单向：`presentation → data → core`，`core` 不反向依赖任何 UI。
`StorageGateway` 是唯一碰 `ContentResolver` 的地方，便于替换实现（例如未来接 MediaStore）。

### 4.1 一次"粘贴"的完整链路

```
点按「粘贴」
  → VM.paste()
    → 读 ClipboardState(mode, entries, sourceLocation)
    → viewModelScope.launch { operator.copy/move(...) }
      → IO 线程：预检空间 → 遍历 → 128KB 缓冲拷贝 → 每块检查取消
        → onProgress 回调（80ms 节流）→ _progress (StateFlow)
    → 完成：repo.invalidate(当前目录) → refresh() → _undo = DeleteCreated(created)
  → UI：ProgressOverlay 随 progress 更新；完成后 UndoBar 出现 6 秒
```

## 5. 存储访问模型

### 5.1 双通道

| 场景 | 实现 | 性能 |
|---|---|---|
| 应用沙盒（`filesDir` / `getExternalFilesDir`） | `java.io.File` | 一次 `listFiles()`，最快 |
| SAF 授权目录 | `DocumentsContract` + **单次** child-documents cursor | 1 次跨进程查询拿全 size/mtime/mime |
| 子目录遍历 | `buildChildDocumentsUriUsingTree(tree, docId)` | 避免 `DocumentFile` 的 N+1 |

`Location` 必须同时携带 `uri`（document uri）与 `treeUri`：
SAF 的子文档只能通过 tree 构造，丢了 tree 就只能读一层。

### 5.2 权限矩阵

| 能力 | 需要权限 | 本应用是否申请 |
|---|---|---|
| 读写沙盒 | 无 | — |
| 读写用户指定目录 | `ACTION_OPEN_DOCUMENT_TREE` + 持久化授权 | 是（运行时由用户选择） |
| 读取全盘 | `MANAGE_EXTERNAL_STORAGE` | **否** |
| 安装 APK | `REQUEST_INSTALL_PACKAGES` + 用户允许未知来源 | 是 |
| 局域网发现/传输 | `INTERNET` / `ACCESS_NETWORK_STATE` / `CHANGE_WIFI_MULTICAST_STATE` | 是 |
| 息屏传输 | `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_DATA_SYNC` | 是 |
| 媒体库 | `READ_MEDIA_*` | **否**（分享走 FileProvider 临时授权） |

### 5.3 如果一定要 `MANAGE_EXTERNAL_STORAGE`：Play 合规怎么写

Google Play 的 `All files access` 政策只接受三类用途，且需在 Play Console 提交声明与演示视频：

1. 文件管理器（**核心功能就是浏览/管理整机文件**）；
2. 备份/恢复类应用；
3. 防病毒/文档搜索类。

声明要点（可直接复用）：
> 本应用的核心功能是设备本地文件管理。用户需要在单一界面内浏览、复制、移动、压缩、
> 解压、重命名设备上的文件。使用 SAF 时，用户必须为每个目录单独授权，无法跨目录执行
> 移动/比较等操作，这直接破坏了文件管理器的核心用例。应用不会上传、分析或共享任何
> 用户文件；`MANAGE_EXTERNAL_STORAGE` 仅用于本地文件读写。

**本项目的选择**：不申请。原因有两条——
(a) 手表上"跨目录批量移动"是低频操作，SAF 的授权成本可以接受；
(b) 全盘权限会让应用在审核队列里多等数周，而收益只是"少点两次授权"。

## 6. 性能与功耗

### 6.1 预算

| 指标 | 目标 | 手段 |
|---|---|---|
| 冷启动到可交互 | < 700ms | 单 Activity、无 DI 框架、DataStore 异步预热 |
| 目录首次加载（200 项 SAF） | < 120ms | 单 cursor 查询 |
| 目录二次加载 | < 20ms | LRU 缓存（24 个目录） |
| 列表滚动 | 60fps | 首屏 60 项 + 滚到底追加；`ScalingLazyColumn` 懒组合 |
| 常驻内存 | < 120MB | 缩略图内存缓存 12%、文本预览上限 200KB、不持有 DocumentFile |
| 息屏待机 | 无后台任务 | 离开设备页立即停止 NSD；回收站清理只在启动时跑一次 |

### 6.2 列表性能

- **分页**：`visibleCount` 从 60 开始，`centerItemIndex >= visibleCount - 8` 时追加一页。
- **DiffUtil**：Compose 场景不用 `DiffUtil`，等价手段是
  `items(key = { entries[it].key })` + 不可变数据类 —— 键稳定 ⇒ 复用组合、避免整表重建。
  （若迁移到 RecyclerView，则用 `ListAdapter + DiffUtil.ItemCallback`，比较字段为 `uri/name/size/lastModified`。）
- **排序/筛选在内存做**：缓存的是原始列表，切排序不重新读盘。
- **失效策略**：任何写操作后 `repo.invalidate(当前目录)`，不做 mtime 智能失效——
  SAF 的 `lastModified` 只有秒级精度，靠它判断会漏掉"同一秒内被删除"。

### 6.3 低电量降级

`OpProgress` 与列表都走同一套状态，降级通过"少做事"实现，而不是改 UI 结构：

| 触发 | 降级动作 |
|---|---|
| 电量 < 15% 或系统省电模式 | 关闭视频首帧缩略图（`VideoFrameDecoder` 不再参与），列表只显示类型徽标 |
| 同上 | 图片缩略图尺寸从 96px 降到 48px，禁用 crossfade |
| 同上 | 大文件操作（>200MB）改为"仅 Wi-Fi + 充电时"提示，不自动开始 |
| 息屏 | 停止 NSD 与滚动轨动画；传输由前台服务保活，UI 不参与 |

## 7. 文件操作

### 7.1 语义

| 操作 | 实现要点 |
|---|---|
| 复制 | 递归 + 128KB 缓冲；目标重名自动 `name (1).ext`（保留两者最安全） |
| 移动 | 同卷沙盒走 `renameTo` 快路径；跨 provider 一律"复制成功后再删源" |
| 重命名 | 只改名字，不改扩展名（UI 层把扩展名单独展示，避免误删 `.jpg`） |
| 删除 | 移入 `files/trash/<uuid>/payload` + `meta.json`，可恢复 |
| 新建 | 文件夹/空文件，重名直接拒绝并提示 |

### 7.2 不破坏数据的四条保证

1. **先写后删**：移动跨卷时，只有目标写入并 flush 成功才删源。
2. **失败可读**：所有异常在 IO 层转成中文原因（"没有写权限""空间不足：需要 1.2GB，剩余 300MB"），UI 不出现异常类名。
3. **可撤销**：删除 → `RestoreFromTrash`；复制 → `DeleteCreated`（删除本次新建的 Uri）。
4. **不静默覆盖**：默认保留两者；覆盖只能通过显式确认（`ConfirmKind.OVERWRITE`）。

### 7.3 进度与取消

- 回调 80ms 节流（≈12 次/秒），避免"进度更新"本身成为卡顿源；
- 每 128KB 检查一次取消标记，取消后立即停止并保留已完成部分；
- 压缩/解压/移动/安装包操作前必弹确认（含体积、目标位置、预计影响）。

## 8. 压缩格式

### 8.1 能力矩阵

| 能力 | ZIP | 7z | 说明 |
|---|---|---|---|
| 创建 | ✅ commons-compress | ✅ commons-compress | 逐字节可控 ⇒ 真实进度 + 即时取消 |
| 解压 | ✅ zip4j | ✅ commons-compress | 逐 entry 流式写目标 |
| 加密读取 | ✅ AES-256 / ZipCrypto | ✅ AES | 密码错误 → "密码错误或包已损坏" |
| 加密创建 | ✅ AES-256（zip4j） | ⚠️ 暂不支持 | 7z 写加密需手工拼 AES 编码器，v1 明确不支持并提示 |
| 分卷读取 | ✅ `.z01/.z02/.zip` | ❌ | 7z 分卷（`.7z.001`）检测后给出可读结论，不假装支持 |
| 分卷创建 | ⏳ 预留 `setSplitLength` | ❌ | UI 未开放 |
| 大文件 | 流式，内存占用恒定 | 流式 | 7z 随机访问需先落 cache |

### 8.2 安全防护

| 威胁 | 防护 |
|---|---|
| zip-slip（`../../etc/passwd`） | entry 名消毒：拒绝绝对路径、盘符、含 `..` 的段 |
| zip bomb | 解压总量上限 = 包体 × 8 + 1GB；entry 数上限 10000；超限立即中止 |
| 空间不足 | 目标为沙盒时先 `usableSpace` 预检，不足直接拒绝并给出数字 |
| 半成品残留 | 压缩先写 `cache/arc-stage`，成功后才落目标目录；失败删除临时文件 |

### 8.3 已知限制（写在这里而不是藏着）

- 7z 加密**创建**未开放（读取支持）；UI 会明确提示改用 ZIP 加密。
- 7z 分卷不支持合并解压；`.7z.001` 会给出"请在电脑上合并"的说明。
- 空目录不会被写入压缩包（ZIP/7z 均按"有内容的条目"生成）。

## 9. 安装包

### 9.1 校验链

```
选中 .apk
 → 落到 cache/apk-stage（PackageManager 只能读文件路径，不能读 content://）
 → getPackageArchiveInfo(GET_SIGNING_CERTIFICATES | GET_PERMISSIONS)
 → 计算每个签名证书的 SHA-256
 → 与已安装版本比对：版本号（升级/降级/同版）、签名摘要
 → 校验 minSdk ≤ Build.VERSION.SDK_INT
 → 检查 canRequestPackageInstalls()
 → 汇总成 ApkInfo（含 blockReason 与 warnings）
```

### 9.2 分包安装

`.apks` / `.xapk` / `.apkm` 本质是 ZIP：
展开出 `base.apk` + `split_config.*.apk` → `PackageInstaller.Session` 依次 `openWrite` 写入 →
`commit(PendingIntent → ApkInstallReceiver)`。
同目录若存在 `split_*.apk`，也会被识别为同一次安装的一部分。

### 9.3 静默安装的边界（明确写死）

> **本应用不做静默安装。**
> 静默安装（`INSTALL_PACKAGES`）只授予系统签名应用或 Device Owner / Profile Owner，
> 普通应用无法获得，也不应该通过任何手段绕过。
> 用户路径永远是：点「安装」→ 系统安装器弹出确认 → 用户确认 → 安装完成。

### 9.4 失败原因映射

| 系统状态码 | 展示文案 |
|---|---|
| `STATUS_FAILURE_CONFLICT` | 与已安装版本冲突（签名或版本不一致） |
| `STATUS_FAILURE_INCOMPATIBLE` | 与当前系统不兼容 |
| `STATUS_FAILURE_INVALID` | 安装包无效或已损坏 |
| `STATUS_FAILURE_STORAGE` | 存储空间不足 |
| `STATUS_FAILURE_BLOCKED` | 安装被系统策略阻止 |
| 无签名 / minSdk 过高 | 安装前就拦截，给出具体数字 |

## 10. 局域网传输

### 10.1 帧格式

```
控制帧：[4B 大端长度][UTF-8 JSON]
数据帧：控制帧 {"t":"chunk","len":N} + N 字节裸数据（N ≤ 64KB）
```

消息：`hello / ready / bye / offer / accept / file_begin / file_resume / chunk / file_end / file_ok / file_bad`。

### 10.2 时序

```
发送方                                     接收方
  ── hello{id,name} ───────────────────▶
  ◀──────────────── hello{id,name,code} ──   双方屏幕显示同一 4 位码
  ── offer[items(id,name,size)] ───────▶
                                          （本机用户点「接受」/「拒绝」，60s 超时自动拒绝）
  ◀──────────────── ready{ok:true} ──────
  ◀──────────────── accept[ids] ─────────
  ── file_begin{id,name,size} ─────────▶
  ◀──────────────── file_resume{offset} ─   断点续传：从 offset 开始
  ── chunk × N ────────────────────────▶
  ── file_end{sha256} ─────────────────▶
                                          （落盘后整体重算 SHA-256 比对）
  ◀──────────────── file_ok / file_bad ──
  ── bye ──────────────────────────────▶
```

### 10.3 断点续传与校验

- `fileId = SHA-256(name|size|mtime)[0..16]`：内容标识跨会话稳定；
- 接收方把未完成数据写到 `LanInbox/.parts/<id>.part`，重连时 `offset = part.length()`；
- 发送方先整文件算一次摘要（多一次读盘），保证续传后仍能给出**整文件**校验和；
- 接收方把已有前缀重新喂进摘要再继续写，最终比对整文件 SHA-256；
- 校验失败 → 删除 `.part` 并回 `file_bad`，绝不留下"看起来完成了"的坏文件。

### 10.4 配对与威胁模型

| 威胁 | 缓解 |
|---|---|
| 同名设备钓鱼 | 双方显示同一 4 位码，接收方必须肉眼核对 + 显式接受 |
| 陌生设备推送 | 默认不监听；进入"设备"页才开服；60s 无响应自动拒绝 |
| 传输被旁听 | **未加密**（明确告知）：同 Wi-Fi 内明文直连。见 §12 演进 |
| 元数据泄露 | TXT 记录只带随机 deviceId + 协议版本；服务名只带用户自填设备名 |

隐私提示直接显示在设备页："仅局域网直连，文件不经过服务器；接收前需本机确认。"

## 12. M3E 组件映射

「M3E」在本项目里指官方 **`androidx.wear.compose.material3`**（Material 3 Expressive for Wear OS），
不是第三方库。UI 的每一层都由它承担：

| 界面职责 | M3E 组件 | 说明 |
|---|---|---|
| 全局骨架 / 背景 / **全局时钟** | `AppScaffold(timeText = { TimeText() })` | 时钟只在这一处声明一次，所有页面共享 |
| 单页骨架 | `ScreenScaffold(scrollState, edgeButton, scrollIndicator)` | 自带时钟槽、滚动指示器、底部边缘按钮位 |
| 时钟 | `TimeText(maxSweepAngle, backgroundColor, content)` | 官方时钟组件 |
| 文件行 | `Card(onClick, onLongClick, contentPadding, colors)` | 长按进多选直接用官方 `onLongClick` |
| 菜单入口行 | `Card` + `Icon(painter)` | 图标用官方 Material 图标 |
| 开关 | `SwitchButton(checked, onCheckedChange, label)` | 自带按下形变与触感 |
| 单选（排序） | `RadioButton(selected, onSelect, label)` | |
| 多选筛选 | `TextToggleButton(checked, onCheckedChange)` | 官方 chip |
| 确认弹层 | `AlertDialog(visible, onDismissRequest, confirmButton, dismissButton, title, text, icon)` | 删除/压缩/解压/安装全走它 |
| 进度弹层 | `Dialog` + `CircularProgressIndicator` | 可取消 |
| 轻提示 / 撤销条 | `Dialog` | Wear 没有 Snackbar，Dialog 是官方浮层容器 |
| 存储占比 | `Card` + `LinearProgressIndicator` | 取代原来的 264° 背景环 |
| 分组标题 | `ListHeader` | |
| 列表 | `ScalingLazyColumn` | 弧形缩放 + 表冠旋转 |
| 滚动指示 | `ScrollIndicator(state)`（`ScreenScaffold` 默认提供） | 取代自绘"边缘滚动轨" |
| 层级跳转 | `TextButton` | 面包屑非末级 |
| 动作按钮 | `Button` / `FilledTonalButton` / `CompactButton` / `TextButton` | |
| 文本输入 | foundation `BasicTextField` | M3E 手表端没有 TextField 原语 |

**仍然自写、且仅有的三处**（M3E 没有对应原语）：

1. `KindBadge` —— 文件类型徽标的**圆底容器**。图标本身是官方 Material 图标
   （`res/drawable/ic_kind_*.xml`，路径数据逐字复制自 material-icons-extended），
   M3E 没有"类型徽标"这个容器概念；
2. `FileCard` 上的**右滑跨行区间多选**手势 —— 必须知道"跨过了几行"，只能挂在行外层；
3. `SelectionScrim` —— 选择工具条的底部压暗，列表会从工具条下面滚过。

### 12.1 五个实测踩坑（已写进代码注释）

1. **`ScalingLazyColumn` 的 `contentPadding.top` 会被锚定逻辑吃掉**：实测 top=46dp 与 top=120dp
   渲染结果**像素级相同**，内容始终顶到时钟带下面。解法是 `autoCentering = null`
   ＋ 列表首位放一个真实的 `Spacer` 占位项。
2. **`ScreenScaffold` 的 content Box 不是全屏**：在里面 `Modifier.align(BottomCenter)`
   会把工具条顶到页面**顶部**。浮层必须包在 `ScreenScaffold` 外层再 align。
3. **`TimeText` 的 `content: CurvedScope.(String) -> Unit` 不是 @Composable**，
   主题色必须在外面取好再捕获进 lambda。
4. **`LinearProgressIndicator` 的 `strokeWidth` 不得小于 `StrokeWidthSmall`（8dp）**，
   否则末端圆点画不出来，直接抛 `IllegalArgumentException` 崩溃。用官方默认值。
5. **`Card` 的 `onClick` 是第一个参数**，尾随 lambda 会正确绑到 `content`；
   但自建封装的第一个可选参数不能是 `onLongClick`，否则尾随 lambda 会绑错。

### 12.2 密度取舍

M3E `Card` 的默认内边距按"每屏 2~3 项"设计，文件列表需要 3~4 项，
所以统一传 `contentPadding = PaddingValues(horizontal = 12.dp, vertical = 6.dp)`。
这是本项目唯一对 M3E 默认值的系统性偏离，原因写在 `M3E.kt` 注释里。

### 12.3 关于图标

`material-icons-extended` 有 35MB，debug 构建不开 R8，为了十几个图标把包体撑大一倍不划算。
所以只把用到的 **11 个**官方图标的路径数据逐字复制成 `res/drawable/ic_*.xml`（共约 20KB），
渲染结果与官方一致；`material-icons-core` 里有的图标（Delete / Search / Send / Star / Share /
Done / Clear / Edit / Refresh / Settings / Add / Lock / DateRange / CheckCircle …）直接用
`Icons.Filled.*`。

## 13. 待确认项决议

| 原需求中的不确定项 | 决议 | 理由 |
|---|---|---|
| 【P2】"应用"分类 + 提取 APK | **不做"应用"分类；不做"提取其他应用 APK"** | ① 手表上没有"已安装应用"的管理诉求；② 提取第三方 APK 涉及分发风险。保留"安装包"分类，只解析用户自己选中的文件。见 §9 的合规边界 |
| 手写"存/转"（发送） | 统一为**「发送」**，落到局域网设备页 | "存"与"复制"语义重复，"转"含义模糊；单一动词降低学习成本 |
| 多开页面 / 多标签 | **不做多标签**，用"切换位置"（快捷菜单内的根目录列表）+ 页面栈替代 | 圆屏上标签栏无处安放；目录栈本身就是天然的"多开" |
| 复制/粘贴/输入路径右侧小字备注 | **保留**：菜单项副标题显示"剪贴板：3 项 · 12.4MB""精确跳转 / 访问已授权目录" | 小字是手表上唯一能承载"当前状态"的位置 |
| 排序偏好是否全局 | **按目录独立记忆**（`sortByPath` map 落 DataStore） | 下载目录按日期、音乐目录按名称，是真实存在的差异 |

## 14. 已知限制

1. 7z 加密创建、7z 分卷合并解压未支持（有明确提示，不静默失败）。
2. 局域网传输为明文；无 TLS（见演进）。
3. 收藏项只存 Uri，若原文件被移动会打开失败（给出可读提示）。
4. 目录不直传（引导先压缩）。
5. 文本查看器不做 Markdown 富文本渲染（手表上收益极低）。

### 后续演进

- **传输加密**：在 `hello` 阶段做 ECDH（P-256）协商会话密钥，数据帧 AES-GCM 加密；
  密钥材料不落盘，配对码只做人工比对。代价是每帧 16B tag + 一次握手，可接受。
- **缩略图磁盘缓存**：Coil 默认已有，若要进一步省电可改为"仅 Wi-Fi 充电时预热"。
- **MediaStore 快速通道**：图片/视频列表可走 MediaStore 查询，比 SAF 快 3~5 倍，
  但需要 `READ_MEDIA_*` 权限——与当前"零存储权限"策略冲突，暂不做。
